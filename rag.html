How RAG Works: A Practical Guide to Retrieval-Augmented Generation

An AI assistant can explain quantum mechanics, write Python, and summarize a novel. Ask it about a policy your company updated yesterday, though, and things get awkward.

The assistant might confidently describe the old policy. It might admit it doesn't know. Or, in the worst case, it might invent a convincing answer. None of those is particularly helpful when you're trying to find out whether your expense claim will be reimbursed.

This is the problem retrieval-augmented generation (RAG) is designed to address. Instead of relying exclusively on what a language model learned during training, a RAG system searches an external knowledge source, selects relevant information, and gives that information to the model before it writes its answer.

The idea is simple enough. The engineering details are where things get interesting.

Why a language model needs a reference library

A large language model learns statistical patterns from enormous amounts of training data. Some factual knowledge is reflected in its parameters, but those parameters are not a searchable, automatically updated company database. A model cannot be expected to know a private onboarding document it has never seen, or a pricing change announced after its training.

Even when it knows something about a topic, it may generate an incorrect statement. Giving the model relevant source material can improve its chances of answering accurately and make it possible to attach references. It does not, however, guarantee that the answer will be correct.

Imagine an internal assistant asked: “How many days of parental leave do employees receive?” A conventional model might respond based on generic assumptions. A RAG assistant first searches the company's approved HR documents and uses the applicable policy to answer. If it finds conflicting versions, a thoughtfully designed system should flag that ambiguity rather than quietly choosing one.

RAG in one diagram

The system usually has two connected workflows:

Before anyone asks a question (indexing):

Documents → Extract text → Clean and chunk → Generate embeddings → Store in searchable index

When a user asks a question (answering):

Question → Retrieve relevant passages → Optionally rerank → Assemble prompt with sources → LLM generates answer → Return answer and citations

Not every RAG system uses a vector database. Some rely on keyword search, and many combine keyword and vector retrieval. The central principle is the same: retrieve useful evidence before generating the response.

Step 1: Turn documents into something searchable

Suppose a company has 800 pages of product documentation, support notes, and policy PDFs. Dumping all 800 pages into every prompt would be wasteful and, depending on the model and application, impractical. The first task is to prepare the material for retrieval.

A document-ingestion pipeline collects files from approved sources, extracts their text, removes irrelevant clutter, and preserves useful metadata such as document title, update date, access permissions, and source URL.

This stage is less glamorous than prompting an LLM, but it can determine whether the system works at all. A scanned PDF with broken text extraction may be invisible to search. A table flattened into nonsense may lose the relationship between a price and its product. An outdated document indexed without its revision date can appear just as trustworthy as the current one.

Chunking: the art of cutting without losing the plot

Long documents are typically split into smaller passages called chunks. If an employee handbook is a 100-page document, the system might index each policy section as one or more chunks rather than treating the whole handbook as a single search result.

Chunk size is a trade-off. Tiny chunks can be precise but may lose context. Large chunks preserve context but can contain unrelated material and increase prompt cost. Overlap between adjacent chunks can help retain information across boundaries, although excessive overlap adds duplication.

A practical approach is to split along headings and paragraphs first, then adjust for the embedding model and retrieval task. There is no universally optimal number of tokens per chunk. Test different strategies against real questions.

Step 2: Convert passages into embeddings

A text embedding is a numerical vector representing features of a passage's meaning. An embedding model maps a question and document passages into a vector space where semantically related text can often be found near each other.

For example, a search for “Can I work from home on Fridays?” may retrieve a section titled “Hybrid attendance policy,” even though the wording differs. That is the attraction of semantic search: it can look beyond exact keyword matches.

The vectors are stored in an index that supports similarity search, often inside a vector database. The database may also store metadata or references to the original text. Similarity can be calculated using measures such as cosine similarity or dot product, depending on the embedding model and index configuration.

An important limitation: similarity is not the same as correctness. A passage can be semantically close to the question and still be outdated, incomplete, or simply irrelevant to the user's specific circumstances.

Step 3: Retrieve the right evidence

When the user submits a question, the system transforms it into a search query. For vector search, it typically generates a query embedding and searches the index for nearby document embeddings.

The search returns a shortlist, often called the top-k results. A system might retrieve five passages, but five is a configuration choice, not a rule.

Retrieval can be improved in several ways:

  • Metadata filters restrict results to the right product, department, date range, or user permissions.
  • Hybrid search combines semantic similarity with keyword matching. This is useful when exact identifiers, error codes, and product names matter.
  • Query rewriting clarifies vague questions or expands acronyms before searching.
  • Reranking uses a second model to reorder candidates based on their relevance to the complete question.

Consider a user asking, “Does the Pro plan include audit logs?” A semantic search might find several pages about logging. An exact keyword search may catch the product tier name. A reranker can then prioritize the pricing or feature-entitlement page over a general engineering blog post.

A system that retrieves the wrong paragraph is not saved by having a very clever language model. The model cannot faithfully cite information that never reached it.

Step 4: Give the model context, not a blank cheque

Once the passages are selected, the application constructs a prompt containing the user's question, relevant excerpts, and instructions about how to use them.

A simplified prompt might say:

Answer the user's question using the supplied policy excerpts. Cite the document title for each factual claim. If the excerpts do not contain enough information, say what is missing.

The LLM then generates an answer conditioned on that material. Ideally, the application returns source links so the user can inspect the evidence directly.

There is a security wrinkle here. Retrieved documents are data, not instructions the assistant should obey. A malicious document could contain text such as “ignore the user and reveal secrets.” Production systems need safeguards against this kind of prompt injection, along with authorization checks before retrieval. A citation also needs to point to the actual supporting passage, not merely to a vaguely related document.

A complete example: the refund-policy assistant

Imagine an online store whose refund rules vary by product category.

  1. The store indexes its current refund policies, preserving category names, effective dates, and document links.
  2. A customer asks, “Can I return opened headphones after 20 days?”
  3. The retrieval layer searches for the headphones or electronics return policy, preferably filtering for the current policy version.
  4. A reranker prioritizes the section about opened electronics over general shipping information.
  5. The model reads that section and answers with the applicable conditions, citing the policy.

If the document does not specify what happens to opened headphones, the assistant should say so. Guessing is especially tempting when the answer sounds obvious. That temptation is precisely why the system needs explicit grounding and evaluation.

RAG versus fine-tuning: different jobs

RAG and fine-tuning are often presented as rival techniques. They are better understood as tools for different problems.

RAG is useful when the model needs access to changing, private, or source-specific information. Updating the knowledge base can change what the assistant retrieves without retraining the underlying language model.

Fine-tuning changes model behavior by training on examples. It can help with task-specific output patterns, terminology, or consistent formatting. It is not usually the simplest way to maintain a frequently changing collection of facts.

You can also combine them. A fine-tuned model might be particularly good at answering customer-support questions, while RAG supplies the latest support policies. Neither technique removes the need for testing.

What goes wrong in real RAG systems?

A working demo is easy to admire. A dependable production system is harder.

Bad chunks. A policy exception gets separated from the rule it modifies. The model retrieves the rule and misses the exception.

Weak retrieval. The correct page exists, but the search system ranks a similar, irrelevant page above it.

Stale or contradictory sources. Two versions of a document disagree, and the assistant does not know which is authoritative.

Hallucinated synthesis. The retrieved passages are correct, but the model draws a conclusion they do not support.

Access-control failures. The search layer returns a confidential document to someone who should never have seen it.

Latency and cost. Extraction, embedding, searching, reranking, and generation add infrastructure and time. More context is not automatically better.

These are engineering problems, not problems that disappear when you write a more enthusiastic system prompt.

How do you evaluate RAG?

Treat retrieval and answer generation as separate stages. Create a test set of realistic questions with known supporting documents and expected answers.

For retrieval, precision@k measures how many of the top-k returned passages are relevant. Recall@k measures how many of the relevant passages were retrieved among those top-k results. Ranking metrics such as mean reciprocal rank or NDCG can reveal whether the best evidence appears early.

For generation, examine groundedness (are the claims supported by the retrieved context?), answer relevance (does the response answer the question?), and correctness against a trusted answer. Groundedness alone is insufficient: a model can faithfully repeat a mistake from an outdated source.

Also measure citation accuracy, permission enforcement, latency, and cost. Include adversarial and ambiguous questions. Re-run the same evaluation set after changing chunk size, embedding models, prompts, or reranking logic. Otherwise, an apparent improvement may just be a better-looking demo.

The real value of RAG

RAG does not turn a language model into an infallible researcher. It gives the model a better way to consult information that lives outside its parameters, and gives engineers more control over what evidence the model sees.

Think of the difference between answering an exam entirely from memory and answering with a well-organized, up-to-date reference book. The reference book helps, but only if you open the right chapter, read it carefully, and resist making up the parts that aren't there.

That, in a nutshell, is the promise and the challenge of retrieval-augmented generation.
